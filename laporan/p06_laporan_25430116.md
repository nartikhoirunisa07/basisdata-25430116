## 2. Ringkasan Dasar Teori

### 2.1 Urutan Pengisian dan Penghapusan Data (DML Integrity)
Data Manipulation Language (DML) terdiri atas `INSERT`, `UPDATE`, `DELETE`, dan `SELECT`. Karena basis data relasional memiliki relasi Kunci Tamu (*Foreign Key*), proses manipulasi data wajib mengikuti aturan ketergantungan relasional:
- **Urutan Pengisian (`INSERT`):** Tabel induk (*parent table*) wajib diisi terlebih dahulu sebelum tabel anak (*child table*). Sebagai contoh, data pada `kategori`, `pelanggan`, `kurir`, dan `produk` harus sudah ada sebelum baris pada `pesanan` dan `detail_pesanan` dapat dimasukkan.
- **Urutan Penghapusan (`DELETE`):** Tabel anak harus dihapus terlebih dahulu sebelum tabel induk dapat dihapus, kecuali relasi tersebut secara eksplisit menggunakan aturan `ON DELETE CASCADE`. Jika relasi menggunakan `ON DELETE RESTRICT`, server akan menolak penghapusan data induk yang masih dirujuk oleh data transaksi.

### 2.2 Bahaya Modifikasi Massal dan Mode Aman (`sql_safe_updates`)
Perintah `UPDATE` atau `DELETE` yang dieksekusi tanpa klausa `WHERE` secara default akan memodifikasi atau menghapus seluruh baris data di dalam tabel tanpa memunculkan pesan peringatan. Variabel sistem `sql_safe_updates` membuat server MariaDB/MySQL menolak perintah modifikasi kecuali:
1. Klausa `WHERE` secara eksplisit menggunakan kolom kunci primer (*key column*), atau
2. Perintah disertai dengan klausa pembatas jumlah baris `LIMIT`.

### 2.3 Pengujian Basis Data: Positif, Negatif, dan Utang Desain
Sesuai unit kompetensi SKKNI **Membuat Basis Data (J.62DMS00.010.1)** Elemen 2, basis data harus diuji ketangguhannya:
- **Uji Positif:** Menguji skenario data yang valid untuk memastikan fungsionalitas sistem berjalan sebagaimana mestinya.
- **Uji Negatif:** Memasukkan data ilegal atau menyalahi aturan untuk membuktikan bahwa server menolak data tersebut dengan kode galat (*error code*) yang spesifik.
- **Uji Gagal & Utang Desain (*Design Debt*):** Mengidentifikasi aturan bisnis kompleks lintas-tabel (*cross-table*) yang belum dapat dicegah oleh constraint deklaratif standar (`CHECK` intra-row), untuk kemudian dijadwalkan penyelesaiannya pada modul berikutnya menggunakan *Database Trigger*.

## 3. Pembahasan Titik Analisis & Latihan Modul 6

### 3.1 Titik Analisis 1: Keamanan `INSERT ... SELECT` dan Imutabilitas Snapshot Harga
**Pertanyaan:** *Mengapa cara INSERT ... SELECT lebih aman daripada mengetik angka manual? Setelah harga naik minggu depan, apakah nota transaksi ikut berubah?*
- **Jawaban:**
  1. **Keamanan & Konsistensi Data:** Menggunakan `INSERT ... SELECT` dari tabel katalog produk secara langsung mengeliminasi risiko kesalahan manusia (*human error / typo*), menjamin bahwa harga satuan yang dicatat pada nota transaksi adalah harga resmi yang berlaku pada katalog master saat transaksi dibuat.
  2. **Imutabilitas Transaksi Masa Lalu (*Historical Snapshot*):** Nota pesanan yang sudah tercatat **TIDAK AKAN IKUT BERUBAH** ketika harga katalog naik di masa mendatang. Hal ini karena kolom `harga_satuan` pada tabel `detail_pesanan` menyimpan salinan nilai fisik saat transaksi terjadi. Sesuai prinsip dasar akuntansi, catatan transaksi keuangan bersifat *immutable* (tidak dapat diubah oleh fluktuasi harga masa depan) untuk menjamin keabsahan audit pembukuan.

### 3.2 Titik Analisis 2: Perilaku `CASCADE` vs `RESTRICT` dan Manajemen Akun Nonaktif
**Pertanyaan:** *Menghapus nota menghapus detailnya, tetapi menghapus petugas/pelanggan ditolak. Jelaskan kedua perilaku ini dari definisi constraint Modul 5. Bagaimana cara yang benar jika seorang staf/petugas berhenti bekerja?*
- **Jawaban:**
  1. **Penjelasan Constraint:**
     - Relasi `pesanan` $\rightarrow$ `detail_pesanan` didefinisikan dengan `ON DELETE CASCADE`. Secara semantik, item detail belanja merupakan entitas dependen (*weak entity*) yang tidak memiliki arti tanpa adanya kepala pesanan. Saat pesanan dihapus, detail belanjanya otomatis dibersihkan agar tidak meninggalkan baris yatim (*orphaned records*).
     - Relasi `pelanggan` $\rightarrow$ `pesanan` didefinisikan dengan `ON DELETE RESTRICT`. Tujuannya adalah auditabilitas sejarah: riwayat transaksi finansial toko tidak boleh kehilangan identitas entitas yang bertransaksi. Server menolak penghapusan baris induk pelanggan jika masih memiliki rekaman transaksi anak.
  2. **Prosedur Staf Berhenti / Konsumen Berhenti:**
     Jangan pernah melakukan penghapusan fisik (*hard delete*) pada data master yang telah bertransaksi. Praktik standar industri adalah menggunakan mekanisme **Soft Delete** atau penonaktifan status, misalnya mengubah kolom `status_akun` dari `'aktif'` menjadi `'nonaktif'`. Dengan cara ini, akun tersebut tidak dapat lagi melakukan transaksi baru, namun riwayat transaksi masa lalunya tetap utuh untuk kepentingan laporan keuangan dan audit.

### 3.3 Titik Analisis 3: Keterbatasan Constraint CHECK dan Rencana Trigger
**Pertanyaan:** *Semua uji positif dan negatif berstatus LULUS. Tuliskan satu uji yang diperkirakan GAGAL karena aturan bisnisnya belum dijaga server (misal penjualan melebihi stok). Mengapa constraint CHECK di tabel produk tidak mencegahnya?*
- **Jawaban:**
  1. **Evaluasi Tuple Tunggal (*Intra-Row Evaluation*):** Berdasarkan standar ANSI SQL, klausa `CHECK` pada definisi tabel beroperasi secara lokal pada baris yang sedang dimanipulasi. Constraint `chk_produk_stok (stok_produk >= 0)` hanya dievaluasi ketika tabel `produk` diubah atau ditambah.
  2. **Ketiadaan Evaluasi Lintas-Tabel (*Cross-Table Subquery*):** Saat operasi `INSERT` terjadi pada tabel `detail_pesanan`, konstrain yang dievaluasi hanyalah `chk_detail_qty (qty_beli >= 1 AND qty_beli <= 10)`. Mesin MariaDB/MySQL **tidak mengizinkan** klausa `CHECK` menjalankan kueri subquery ke tabel lain (seperti `SELECT stok_produk FROM produk`) untuk memverifikasi apakah sisa stok masih mencukupi.
  3. **Konsekuensi:** Server tetap menerima (`Query OK`) penyimpanan transaksi pembelian dengan jumlah melebihi sisa stok fisik di gudang. Aturan bisnis ini memerlukan mekanisme kontrol prosedural tingkat lanjut, yaitu **Database Trigger (`BEFORE INSERT ON detail_pesanan`)**, yang dijadwalkan sebagai Utang Desain pada **Modul 14**.

### 3.4 Jawaban Latihan dan Modifikasi E

#### Latihan E.1: Pengarsipan Anggota Nonaktif Tanpa Menghapus Data Transaksi
```sql
-- 1. Membuat struktur tabel arsip identik dengan struktur tabel pelanggan
CREATE TABLE IF NOT EXISTS pelanggan_arsip LIKE pelanggan;

-- 2. Memindahkan data anggota nonaktif yang mendaftar sebelum tahun 2026
INSERT INTO pelanggan_arsip
SELECT * FROM pelanggan
WHERE tgl_registrasi < '2026-01-01 00:00:00';

-- 3. Menghapus dari tabel asal HANYA jika anggota TIDAK memiliki riwayat transaksi pesanan
DELETE FROM pelanggan
WHERE tgl_registrasi < '2026-01-01 00:00:00'
  AND id_pelanggan NOT IN (SELECT DISTINCT id_pelanggan FROM pesanan);
```

#### Latihan E.2: UPDATE Harga Kategori Makanan Naik 5% Dibulatkan ke Ratusan Terdekat
```sql
UPDATE produk 
SET harga_katalog = ROUND(harga_katalog * 1.05, -2)
WHERE id_kategori = (SELECT id_kategori FROM kategori WHERE nama_kategori = 'Pakaian Pria')
  AND id_produk > 0;
```
*(Catatan: Penggunaan fungsi `ROUND(..., -2)` membulatkan nilai moneter ke ratusan terdekat, misalnya Rp157.500 dibulatkan menjadi Rp157.500 atau Rp152.340 menjadi Rp152.300. Klausa `id_produk > 0` disertakan agar mematuhi safe update mode).*

### 4.2 Struktur dan Rekapitulasi Data Sampel (`p06_data_25430116.sql`)
Skrip `p06_data_25430116.sql` dirancang secara sistematis dengan data realistis Indonesia (tanpa nilai fiktif sembarangan seperti "abc" atau "test1") untuk menopang seluruh kebutuhan kueri Pertemuan 07 hingga 15.

Berikut adalah rekapitulasi jumlah baris fisik per tabel yang berhasil dieksekusi ke dalam MariaDB:

```sql

UNION ALL SELECT 'kurir', COUNT(*) FROM kurir
UNION ALL SELECT 'pelanggan', COUNT(*) FROM pelanggan
UNION ALL SELECT 'produk', COUNT(*) FROM produk
UNION ALL SELECT 'pesanan', COUNT(*) FROM pesanan
UNION ALL SELECT 'detail_pesanan', COUNT(*) FROM detail_pesanan
UNION ALL SELECT 'pembayaran', COUNT(*) FROM pembayaran
UNION ALL SELECT 'pengiriman', COUNT(*) FROM pengiriman;
```


### 4.3 Verifikasi Distribusi Tanggal Transaksi Utama
```sql
SELECT 
    DATE(tgl_pesanan) AS tgl_transaksi, 
    COUNT(*) AS jumlah_pesanan, 
    MIN(total_bayar) AS min_bayar, 
    MAX(total_bayar) AS max_bayar, 
    SUM(total_bayar) AS grand_total

GROUP BY DATE(tgl_pesanan);
```
